      A verdict a business owner and a pipeline can both read

      A staircase of 50 → 400 users on shop-api. The first line is for the business; "Read with care" lists everything it rests on.

      verdict.md

      # Verdict: WARN It holds 200 users (412 requests/s) within the SLA; the planned peak is 180, so the headroom is 1.1×. | users | rps | p95 ms | error rate | within SLA | | 50 | 104 | 88 | 0 | yes | | 100 | 207 | 96 | 0 | yes | | 200 | 412 | 171 | 0.001 | yes | | 400 | 431 | 1840 | 0.034 | no | ## Read with care - WARN: capacity 200 users leaves only 11 % headroom over the planned peak of 180 - environment parity: staging, half of production - SLOs not agreed with an owner: search

      Four outcomes, one exit code each

      OutcomeWhenExit
      PASSevery planned transaction within its SLO; no regression0
      WARNan SLO missed with the SLA met; a heavy tail; little headroom0
      FAILan SLA breached; a regression above noise; capacity below the peak; the target died1
      NOT EVALUABLEa gate failed; no baseline; the generator saturated; a worker lost3

      Each run has its own folder: verdict.md, analysis.md, result.json (perf-result/v1), and junit.xml for CI.

      Finding the cause

      From "it got slow" to "the pool was full"

      The analysis finds the knee, where p95 more than doubles while throughput stops growing. Then it reads what the target was doing at that moment.

      Without signals

      ## Bottleneck not CPU in api: it stayed under 85 % while latency rose. The wait is in a pool, locks, a slow dependency or I/O, or in a part that was not monitored. Evidence: p95 96 -> 1840 ms at t=600s, rps flat at 431, CPU max 38 % (api).

      Honest, but it leaves a person to dig through dashboards.

      With signals from /metrics or Prometheus

      ## Bottleneck waiting on db_pool: a connection pool was full: requests waited for a connection. Evidence: p95 96 -> 1840 ms at t=600s, rps flat at 431, CPU max 38 % (api), db_pool 100 % > 95; under their limits then: locks. ## Signals | Signal | Kind | Highest | Limit | First above | | db_pool | pool_used_pct | 100 % | 95 | t=598s | | locks | db_locks_waiting | 0 locks | 0 | never |

      The cause is named, with the reading that proves it. A signal that stayed quiet is ruled out by name.

      What the signals cover

      pool_used_pctpool_waitingdb_locks_waitingdb_slow_queriesgc_time_pctevent_loop_lag_msthread_pool_queuequeue_depthcustom

      They are read from HikariCP, prom-client, prometheus-net, postgres_exporter, mysqld_exporter, or any Prometheus query.

      The loop that keeps it honest

      It fixes its own mistakes, and checks the fix

      Every judged run teaches. What ai-perf got wrong in making the load is fixed in the next run; what only a person can fix is said so.

      $ perf run load.json --until-evaluable attempt 1: NOT EVALUABLE w0 at 97 % CPU in the measured window fix: workers 2 -> 4 (problem:generator_saturated) attempt 2: PASS fix verified by this run the spec file still says 2 workers; learned.json says 4

      What it fixes, and what it never touches

      • Fixed by itself: a saturated generator gets more workers, a late engine a longer rampdown, dropped arrivals a higher VU cap.
      • Checked: the next full run verifies the fix. After two recurrences it is rolled back and a person is asked.
      • Never touched: the system under test, the planned load, the SLOs or the environment.
      • Remembered: perf brief holds the project on one page of about 1500 tokens. perf share sends the lessons to the team's Recall.
